# Error Handling — A Strategy, Not Try/Catch Sprinkled

> Every error is one of four things: expected business outcome,
> transient infrastructure fault, programmer bug, or hostile input.
> Each demands a different response. Lumping them together is the
> source of most "mysterious" outages.

## The four error categories

| Category | Example | Strategy |
|---|---|---|
| Expected business outcome | "Card declined", "Email already exists" | Return as data — not an exception. Type it. |
| Transient fault | Network blip, DB timeout, 503 from dependency | Retry with backoff + jitter, then circuit breaker |
| Programmer bug | NPE, KeyError, off-by-one | Fail fast, log loudly, alert, FIX IN CODE |
| Hostile input | Malformed JSON, SQL injection attempt | 4xx with safe message, log fingerprint, rate-limit |

**Default-everywhere `try/except: pass` collapses all four into
"silently broken."** Each category has a different response. Code
should make the category obvious at the call site.

## Errors as data — the senior move

In languages that support it (Rust `Result`, Haskell `Either`,
Go's `(value, error)`, TypeScript `Result<T, E>` libs), prefer
returning errors as values for the EXPECTED business outcomes.

```typescript
// good — caller can't ignore the error
function chargeCard(...): Result<Payment, ChargeError> { ... }

const r = chargeCard(...);
switch (r.kind) {
  case "ok":   return success(r.value);
  case "declined": return userMessage("Card declined");
  case "expired":  return userMessage("Card expired");
  case "fraud":    return blockTenant(r.error);
}
```

vs.

```typescript
// bad — what does this throw? Reader doesn't know.
try {
  const p = await chargeCard(...);
  return success(p);
} catch (e) {
  // is this declined? network error? bug?
  return userMessage("Something went wrong");
}
```

Exceptions are still right for *exceptional* things (programmer
bugs, fatal asserts). Don't use them as control flow for business
outcomes the caller routinely sees.

## Retry — the careful art

Transient faults need retry. But retries CAUSE outages too.

Rules:

1. **Only retry idempotent operations.** Or operations with
   idempotency keys. Otherwise: double-charge.
2. **Exponential backoff with FULL JITTER** (Marc Brooker, AWS):
   ```
   sleep = random_uniform(0, min(max_delay, base * 2 ** attempt))
   ```
   Without jitter, retries synchronize across clients and DDOS the
   downstream.
3. **Bound the total time, not the attempt count.** "Retry for up
   to 30 seconds" is a useful budget; "10 retries" can be 10ms or
   10 minutes depending on backoff.
4. **Categorize before retrying.** 5xx → retry. 4xx → don't (it
   won't get fairer next time). 429 → respect Retry-After header.
5. **Stop retrying when a circuit breaker opens.** See
   `circuit_breaker_bulkhead`.

## Idempotency keys (the only way to retry writes safely)

```
POST /payments
Idempotency-Key: 7c8f2a-... (client-generated UUID)
```

Server: store (key, response) for 24h. Re-submit with same key
returns the SAME stored response, not a new charge. The retry
budget is now safe.

Critical: the idempotency key is generated by the CLIENT and
persisted BEFORE the network call. If you generate it
server-side, retries can't reuse it.

## Error propagation across boundaries

When error crosses a process boundary, it loses fidelity:

```
[DB driver]
  raises ConnectionRefused
       ↓
[Repository]
  rethrows as RepositoryError("save failed")
       ↓
[Service]
  rethrows as ServiceError("order processing unavailable")
       ↓
[HTTP handler]
  returns 503 Service Unavailable + RequestId X
```

At each layer:
- **Wrap, don't swallow.** Preserve the cause chain.
- **Translate** to the abstraction level — `RepositoryError` not
  `ConnectionRefused` at the service layer.
- **Tag with a stable code** so observability can pivot.
- **Carry a request ID** end-to-end so support can correlate.

When the error reaches the user:
- Human-readable, actionable message ("we couldn't process your
  payment, your card was not charged").
- A short opaque error code for support.
- NEVER the stack trace or internal class names.

## Logging errors — the minimum bar

Each logged error must have:

- Severity (DEBUG / WARN / ERROR / FATAL).
- A stable error code or class.
- The fingerprint variables (user id, tenant id, request id, what
  was attempted).
- The full stack trace, if it's an unexpected failure.
- NO sensitive data (PII, secrets, tokens). Log redaction is not
  optional.

Search for ERROR logs that share a fingerprint daily — that's how
you find systemic issues before they become incidents.

## The four severities (and what they mean)

| Severity | Meaning | Page? |
|---|---|---|
| DEBUG | Verbose, for developers | No |
| WARN | Unusual but handled | No |
| ERROR | Operation failed; caller will see failure | Aggregate (page if rate spikes) |
| FATAL | Process can't continue | YES — page immediately |

Many services log everything as ERROR. The dashboard becomes useless
because there are 10k/min. Calibrate severity to "would I want to
be paged for this?"

## Validation guardrails (the boring stuff)

Input validation is error handling's first line:
- Validate at the BOUNDARY (controller, queue consumer), not at the
  bottom of the stack. By the time bad data reaches the DB it's too
  late.
- Use a schema library (zod, pydantic, marshmallow) — declarative
  is more readable and harder to mis-implement than imperative ifs.
- Reject early, with a 4xx and a specific field-level message. Don't
  return a 500 for "missing field."

## Anti-patterns

- **Catch Throwable / Exception / `except:`** without narrowing.
  Swallows OOM, KeyboardInterrupt, programmer bugs. Always catch
  the most specific class.
- **Return `null` for "not found" and `null` for "error".** Caller
  can't tell. Use a typed result.
- **Silent retries that mask data corruption.** A retry that
  succeeds the second time when the first wrote partially is the
  classic dual-write bug.
- **Retry FOREVER.** Compute a budget. Stop. Surface the failure
  upward.
- **Logging the same error 1000x per second.** Sample, rate-limit,
  or aggregate. Or both.
- **Stack trace in the user-facing response.** Information disclosure
  + ugly UX. Status code + opaque code only.
- **Different error formats per endpoint.** Standardize one envelope
  (RFC 7807 problem+json is good) across the entire API.

## RFC 7807 error envelope (use it)

```json
HTTP/1.1 422 Unprocessable Entity
Content-Type: application/problem+json

{
  "type": "https://errors.example.com/payment-card-declined",
  "title": "Card declined",
  "status": 422,
  "detail": "Issuer responded with 'insufficient funds'",
  "instance": "/payments/abc-123",
  "request_id": "01HGZ4..."
}
```

Same envelope for all 4xx/5xx → SDKs and clients write one
parser, not N.

## Validation that error handling is solid

- [ ] No `except:` / `catch (Throwable)` in the codebase.
- [ ] Every write endpoint accepts an idempotency key.
- [ ] Retries have a max-duration budget and use full jitter.
- [ ] User-facing errors have a code, a human message, and never
      a stack trace.
- [ ] You can grep error code → file:line and find the source in
      < 30 seconds.
- [ ] Error dashboard groups by code, not by message string.
